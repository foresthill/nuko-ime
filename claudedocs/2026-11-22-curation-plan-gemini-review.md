## 1. Gemini(Carbon) の分析（一次入力・原文保存）

> 以下は Gemini からの回答の全文。nuko 側の判断・検証は §2 以降に分離して書く。

### 核心の見立て

提示された仮説（**1. Curation層の導入 → 2. ベンチマーク構築 → 3. モデル改善**）の優先順位は、
IME 開発の定石に照らしても筋が通っている。「にんい」の症状（`任意 98996` に対し `ニンニ 97803`）が
示す最大の構造的問題は、**辞書引き候補（Lexical）と機械生成フォールバック（Transliteration）が
同じスコア空間で殴り合っており、かつ機械生成側のベーススコアが高すぎる**（実在語の 7 位
`任に 95764` に勝ってしまっている）点。

### A. 候補リストのノイズ抑制（Curation / Post-processing 層の設計）

`convert()` 直後に「候補キュレーション層（Tiered Ranking + Pruning）」を挟む。スコアの微調整でなく
**候補の出自（Origin）による階層分離**で解くのが定石。

**A-1. 機械生成フォールバックの扱い（Mozc / Google 日本語入力の定石）**
- **半角カタカナの常駐廃止（即効性：特大）**: 現代 IME で通常変換に半角カタカナ `ﾆﾝﾆ` が上位に
  欲しいケースはほぼゼロ。Mozc でも半角カタカナは 1 ページ目に出さず **F8 押下時**または候補末尾の
  「文字種変換枠」のみ。
- **スコア空間の分離（Tier 制）**: 機械生成の全角カタカナ・ひらがな無変換に固定の高スコアを
  与えると実在漢字（`任に 95764`）を押し退ける。階層：
  - Tier 1: 個人学習（王冠）・訂正ヒット
  - Tier 2: 単漢字でない辞書ヒット・統計モデルの有力ラティス解（1 文節〜複合語）
  - Tier 3（T13N スロット）: **主読みの**全角カタカナ 1 件のみ（辞書から同じカタカナ表層が出て
    いれば重複排除）
  - Tier 4: 低スコアな文節切り（`任に` `忍に`）・単漢字群・ひらがなそのまま
  - オンデマンド（F6〜F10 / 最下部）: 半角カタカナ、全角英数
- **【落とし穴】未知のカタカナ語を殺さない**: 「カタカナを候補が尽きた後に回す」をそのまま入れると、
  辞書にない外来語（`りあくと→リアクト`）で `利悪と` 等の無理な漢字分節が上位を埋め、毎回 F7 を
  強いる「**F7 強要問題**」が起きる。
  - 対策: ラティス最小コストが悪化したとき（1 文節で辞書ヒットせず助詞/単漢字の継ぎ接ぎになった
    とき）は**未知語と判定して全角カタカナを 1〜2 位に自動浮上**。1 文節で高信頼の辞書語（`任意`）が
    取れているときはカタカナを 4〜5 位以降／ページ末尾に沈める。

**A-2. `nn` 代替読み（Ambiguous Reading）の剪定ルール**
- 鉄則：**代替読みには Transliteration（機械生成のかな/カタカナ/半角）を一切許可しない**。
  1. 生成時フィルタ: `nn_alternate_readings` から変換を呼ぶ際 `include_transliterations = false`。
     代替読みの存在意義は「曖昧入力から**辞書内の実在語 `任意` を救済**」だけ。`ニンイ/ﾆﾝｲ` を
     欲しいユーザーはいない。
  2. 主読み T13N の降格条件: 代替読み側から「1 文節完結の高スコア辞書語（`任意`）」が見つかり、
     主読み側（`にんに`）に 1 文節辞書語が無いなら、「意図した読みは `にんい`」と事後判定し、
     主読み由来の `ニンニ/にんに` も Tier 4 へ下げる。
- これで `ニンニ/にんに/ﾆﾝﾆ/ニンイ/ﾆﾝｲ` の 5 連ノイズは**単一ルールで消滅**し、
  `1. 任意 / 2. 任に / 3. 忍に / 4. ニンニ(末尾)` に引き締まる。

### B. 本命ランキングの底上げ（ローカル・軽量制約下の現実解）

| アプローチ | 実装コスト | ランタイム負荷 | 配布サイズ増 | ロングテール効き目 |
|---|---|---|---|---|
| 1. 高品質オープン辞書・頻度の蒸留統合 | 低〜中 | ゼロ | 数MB〜十数MB | 大（語彙穴・基本頻度の是正） |
| 2. 品詞クラス N-gram との線形補間 | 中 | 極小 | 数MB | 大（未知文脈の同音異義安定） |
| 3. 上位K件の軽量LMリランキング | 高 | 小（数ms） | 15〜40MB | 特大（文脈理解・長文） |

- **B-1. Mozc/Sudachi 辞書のコスト逆算（最コスパ）**: 自前小規模コーパスは百科事典的語彙に偏り、
  日常語の頻度バランスが歪む。**Mozc システム辞書（BSD-3）**や **SudachiDict/UniDic** の精緻な
  単語コスト・品詞接続コストをベースライン（事前分布）にして平滑化（Dirichlet/バックオフ）に
  使うと順位が落ち着く（ライセンス互換は要確認、BSD-3/Apache-2.0 は MIT と組み合わせやすい）。
- **B-2. 品詞（POS）クラス Bigram のバックオフ強化**: surface bigram は辞書増で組合せ爆発し
  ロングテールが未観測ゼロになる。**品詞細分類 × 品詞細分類の接続コスト行列**（Mozc の
  `connection` 相当）を強化し、単語 bigram 未観測時に POS bigram + unigram へ Kneser-Ney 等で
  バックオフさせると「変な単漢字結合が複合語に勝つ事故」を構造的に防げる。
- **B-3. N-best 軽量ニューラルリランキング（中長期の本命）**: Viterbi で上位 10〜20 件を出した後、
  **Space 押下の瞬間だけ**軽量モデル（量子化極小 GPT-2/RoBERTa、10〜30M params、INT8/Q4 で
  15〜30MB、`candle`/`ort`(ONNX) で Rust 推論）でリランク。Apple Silicon で 1〜3ms。AzooKey の
  `Zenzai` が実証。n-gram で解けない文脈（「本を買う」vs「猫を飼う」）をローカル完結で一網打尽。

### C. 変換精度の評価手法（Whack-a-mole にしない計測基盤）

- **C-1. 評価コーパスの 3 階層**:
  - Golden（必達・回帰 / 300〜500 文）: 開発者が「イラッとした例」＋同音異義定番＋助数詞/日付/`nn`
    境界。**Top-1 98%以上・悪化ゼロ**を CI ゲートに。
  - Silver（一般ドメイン / 5,000〜10,000 文）: 青空文庫は古いので避け、現代語クリーンコーパス
    （UD Japanese GSD、Wikipedia 平易文、CC-100/CommonVoice 書き起こし等）を Sudachi(Mode C)/
    MeCab+UniDic で解析し「読み→正解表層」ペアを自動生成。
    - 【落とし穴】解析器自体の読み誤り（明日=あす/あした、1日=ついたち/いちにち）が数%混じる。
      Silver は絶対値でなく**変更前後のデルタ（+1.2%/-0.3%）を見る温度計**として使う。
- **C-2. 追うべきメトリクス**（Top-1 だけでは 2〜6 位汚染を見逃す）:
  - Top-1/3/5 Recall（文節単位・全文一致）
  - MRR（正解順位の逆数平均）
  - **Lexical Purity @ Top-5**（独自・今回の症状直結）: 上位 5 候補に実在語が占める割合／機械生成
    ノイズが上位 3 位に混入した率
  - **Diff ダンプ**: 前回コミットと比べ Degraded / Improved 一覧を Markdown 出力する CLI
    （`cargo run --bin bench-eval -- --diff baseline.json`）。イテレーション速度が桁違いに上がる。

### D. 提示 UX による「尾の長さ」の隠蔽

- 初期表示件数の制限と段階展開（macOS 標準 / ATOK 方式）: Space 1 回目はインライン 1 位＋候補は
  上位 3〜5 件に抑える、または「有力候補ゾーン」と「文字種変換ゾーン」の間にセパレータ/別タブ。
- 候補下部に固定フッター `[F6: にんい] [F7: ニンイ]` でショートカット逃がし → メイン 1〜9 番を
  純粋な漢字・語彙候補だけにでき、見た目が洗練される。

### 推奨アクションプラン（Gemini 提案）

1. 【即日〜数日】`engine.rs` の Curation 層分離（A の実行＋未知語ガード）
2. 【1 週間】`bench-eval` CLI と 1,000 件ベンチマーク構築（C の実行）
3. 【中期】語彙コストの外部辞書蒸留 ＆ POS 接続コスト見直し（B の実行）

## 2. nuko 側の受け止め・実コードとの照合（随時更新）

### 2.1 ノイズの出所（コードで特定 / 一部は実測で確認予定）

flat `convert()`（`nuko-core/src/conversion/engine.rs`）の候補生成：
- step 4: かなそのまま `score=-100`（`CandidateSource::System`）
- step 5: 全角カタカナ `score=-90`
- step 6: 半角カタカナ `score=-95`
- step 2 `merge_libakaza_candidates`: `nn_alternate_readings(reading)` でループし、**主読み＋各代替読み**
  を libakaza で変換してマージ。各候補に `LIBAKAZA_PRIORITY_BOOST` を加算。

⚠️ **重要な未確認点（実測で確定させる）**: スクショの `ニンニ 97803` 等は **libakaza 帯（~97k）**で、
flat の step 5/6（-90/-95）**ではない**。つまりスクショのノイズは「step 5/6 の機械生成カタカナ」では
なく、**libakaza 自身が代替読み（にんに）に対して返すカタカナ/かな候補**か、あるいは segmented 経路の
出力の可能性が高い。→ **A-1(flat step5/6 削除)だけでは症状が消えない恐れ**。先に下記「実測メモ」で
どの経路・どのスコア帯かを `--release` の `nuko convert にんい --libakaza --personal --explain`
（[[nuko-ime-scoring-transparency]] #183、debug は rsmarisa 再帰で panic するので release 必須）で確定する。

### 2.2 nuko の制約・既存方針との整合

- A（候補 curation）は「どの層で直すか」方針（docs/ARCHITECTURE §3.4）の**規則/提示層**に当たり、
  個別辞書追記を避ける既定方針と完全に整合。最優先・最小リスク。
- A-1 の **Tier 制**は、既存の多数の順位調整（USER_DICT_BOOST / 王冠 / correction / 記号代表 /
  日付形式）が **`score` 加減算 1 本**で積み上がっている現状と衝突しないか要確認。Tier を別フィールドで
  持つか、既存のスコア帯（学習 200k＋ / libakaza ~100k / System 負値）を活かして「機械生成は負値帯に
  戻す」で足りるか、を実測して決める。
- A-1【未知語ガード】（F7 強要回避）は nuko でも必須。`りあくと→リアクト` が沈むと回帰。
  libakaza 側に「1 文節で辞書ヒットしたか／ラティス最小コスト」を返す口があるか要調査
  （`reading_is_single_dict_word` は既にあるので流用可能性）。
- B は中長期。B-3 のニューラルリランクは配布サイズ（15〜30MB）とローカル制約に注意。まず A/C。
- C は「数千件」を定量化する唯一の道。Golden Set は既存の `#[test]` 群（rstest 蓄積方針）と
  相性が良い。bench-eval CLI は `nuko-cli` に追加するのが筋。
- D（提示 UX）は controller.rs / candidate_panel.rs = **IMK 境界に触れるため smoke 必須**
  （[[nuko-ime-hardware-smoke-test-gap]]）。auto-merge 方針では**手動マージ対象**。

## 3. 実測メモ（PR-1、2026-11-22 実測・`--release`）

### 3.1 「にんい」のノイズ出所（確定）

`nuko convert にんい --libakaza --personal --explain --count 12`（実機 learning.json・9416 entries）:

```
変換候補 (flat):
  1. 任意   score=500109 [学習辞書] 学習×6   ← 王冠/学習で最上位
  2. にんい score=97129  [libakaza/静的]      ← 読みのかな（transliteration）
  3. ニンイ score=97129  [libakaza/静的]      ← 全角カナ（transliteration）
  4. ﾆﾝｲ   score=97129  [libakaza/静的]      ← 半角カナ（transliteration）
  5. 任い   score=94422  [libakaza/静的]      ← 実語（漢字）
  6. 忍い   score=94379  [libakaza/静的]
  ...
```

- **確定**: ノイズ `にんい/ニンイ/ﾆﾝｲ` は flat step4/5/6（-100/-90/-95）**ではなく**、
  `merge_libakaza_candidates` が libakaza から受け取った「読みの transliteration 候補」。
  libakaza raw `score=-2871` に `LIBAKAZA_PRIORITY_BOOST=100_000`（engine.rs:86）が乗って
  **97129**。だから実語の漢字（任い 94422）より上に居座る。
- 定数: `LIBAKAZA_PRIORITY_BOOST=100_000` / `USER_DICT_BOOST=200_000` /
  `ALT_READING_KANA_SCORE=-70`。学習帯は 200_000+。
- スクショにあった `ニンニ 97803 / にんに 97129 / ﾆﾝﾆ` は**代替読み にんに**由来の
  transliteration（nn_alternate 展開分）。純かなは line 704 で skip 済みだが**カタカナ/半角は
  素通り**している（A-2 の対象）。

### 3.2 未知語ガードの判別シグナル（確定）

外来語を `--release` で実測（`りあくと/ぷろぐらむ/こーひー`）:

```
りあくと → 1.リアクト 2.Re・Act 3.りあくと 4.ﾘｱｸﾄ 5.リアくと ...
ぷろぐらむ → 1.プログラム 2.ぷろぐらむ 3.ﾌﾟﾛｸﾞﾗﾑ ...
こーひー → 1.コーヒー 2.☕ 3.珈琲 4.こーひー 5.ｺｰﾋｰ ...
```

- 外来語では**最上位がカタカナ自身（リアクト/プログラム/コーヒー＝実語）**。「読みの機械生成だから
  下げる」を無条件に適用すると**リアクトが沈んで毎回 F7 を強いる**（Gemini の F7 強要問題）。
- **判別の結論**: 「**最上位候補が transliteration 形（読みの かな / 全角カナ / 半角カナ のいずれか）か、
  それとも実語か**」で機械判定できる。
  - にんい → 最上位 `任意`（実語）→ `にんい/ニンイ/ﾆﾝｲ` を System 帯へ降格
  - りあくと → 最上位 `リアクト`（transliteration 形＝これが答え）→ 降格しない
- 「候補に漢字が 1 つでもあれば降格」はダメ（`リア久斗` `プログラ無` 等の junk 漢字が常に出るため
  誤発火）。**最上位だけ**を見るのが正しい。

### 3.3 実装方針（確定）

- **curation 関数**（純粋・テスト付き）を `convert()` の sort 直前に挟む:
  `curate_transliterations(&mut CandidateList, reading)`
  1. **半角カタカナ**（`to_halfwidth_katakana(reading)` / 各 alt）は**常に** System 負値帯へ降格
     （Mozc 定石：半角は 1 ページ目に出さない）。
  2. **読みのかな / 全角カタカナ**は、**最上位候補が実語（非 transliteration 形）のときだけ** System 帯へ降格。
     最上位自体が transliteration 形（外来語）なら触らない＝未知語ガード。
- **両経路に配線する**（CLAUDE.md #178/#184 の教訓＝flat だけ直すと segmented で再発）。
  flat `convert()` と segmented（`merge_nn_alternates_into_segments` 後の各 seg 候補）両方。
- A-2（代替読みの transliteration 抑制）は `merge_libakaza_candidates` / segmented の alt ループで
  **alt のカタカナ・半角も skip**（純かなは既に skip 済み）。

### 3.4 bench（C）の既存資産

- `nuko-cli` に **`nuko-bench` バイナリが既存**（Cargo.toml）。C-1/C-2 はこれを拡張する形で着手でき、
  ゼロからではない。PR-4 で中身を確認して Golden Set＋Top-1/MRR/Diff を足す。
