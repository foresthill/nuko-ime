# 文節境界(区切り)評価で分かったこと — 「誤分割」を集めたら自分の正解ラベルが推測だった

**日付**: 2026-11-27
**対象**: nuko-ime 文節境界評価 (`nuko eval --segment`) / Golden Set `eval/golden_seg.tsv`
**関連**: PR #245 (境界評価の実装) / PR #246 (Golden 拡充) / 本ドキュメント (訂正と知見)

---

## 1. 要約 (3行)

- かな漢字変換の精度を「表層 (どの漢字を選ぶか)」とは**別軸**で「区切り (どこで切るか)」として計測する基盤を入れた。
- **誤分割を集めて改善ターゲットにしようとしたら、集めた「正解」の一部が自分の推測で、実は誤りだった** (`きょうはいしゃにいく` は「今日歯医者に行く」が正当)。評価が、対象の品質ではなく**こちらの思い込み**を先に検出した。
- 残る真の難ケース (`にわには…` / `すもも…`) は bigram 言語モデルの限界で、**「は を強制的に切る」ようなパッチは `歯医者/埴輪/母/花/橋` 等の実在語を全部壊す**ので禁じ手。本当のレバーは LM の質。

---

## 2. なぜ区切り評価を作ったか

nuko-ime の変換は 2 経路ある。

- **flat** (`convert`): 単文節・静的辞書
- **segmented** (`convert_segmented`): libakaza の複数文節 Viterbi。**文の大半**を担う

これまで変換精度ベンチ (`nuko eval`、Golden `eval/golden.tsv`) は **表層 Top-1 / MRR / Purity@5** を測っていたが、「どこで切るか」の誤りは **Top-1 を落とす形で間接的にしか見えなかった**。区切りと表層を分けて測れば、「表層は惜しいが区切りで損している / その逆」を切り分けられる。そこで境界評価を足した。

### 指標の定義

- **境界** = 文節間の位置を、読みの**文字数**累積で表す。
  例: `きょう|は|いい|てんき` → 内部境界 `{3, 4, 6}`
- **Precision** = 切った所の正しさ (TP / 予測した境界数)
- **Recall** = 切るべき所を切れたか (TP / 正解の境界数)
- **F1** = その調和平均 (micro 平均)
- **文完全一致率** = 区切りが丸ごと正解した文の割合

純粋関数 (`segmentation_boundaries` / `boundary_counts` / `prf` / `SegCaseResult` / `SegEvalSummary`) は `nuko-core/src/eval.rs` にあり、数値はユニットテストで pin (モデル不要で CI 緑)。予測区切りは実機モデルの `convert_segmented` から取る。

```
cargo run --bin nuko -p nuko-cli --release --features akaza -- \
    eval --segment --libakaza --personal --show-misses
```

## 3. 実測 baseline (2026-11-27, 36 文)

| 指標 | 値 |
|---|---|
| 文完全一致率 | **94.44%** (34/36) |
| 境界 Precision | **100.00%** |
| 境界 Recall | 93.81% |
| 境界 F1 | **96.80%** |

**Precision が 100%** なのが示唆的だ。libakaza は **「切りすぎる (過分割)」ことが一度もなく**、難ケースで **「切り足りない (過結合)」だけ**。つまり誤りの型は一方向に偏っている — 隣接する語を 1 文節に**まとめ過ぎる**。これは後述の「は を実在語に飲み込む」型と一致する。

区切りを外した 2 件:

```
にわにはにわにわとりがいる → 正解 にわ|に|は|にわ|にわとり|が|いる
                             予測 にわ|に|はにわ|にわとり|が|いる
すもももももももものうち   → 正解 すもも|も|もも|も|もも|の|うち
                             予測 すもももももももものうち (全く切れず)
```

## 4. 核心: 評価が最初に検出したのは「自分の推測」だった

PR #246 で「現状誤分割する既知ケース」として 3 文を入れ、**正解を人手で付けた**。そのうちの 1 つ:

```
きょうはいしゃにいく → 正解(当時) きょう|は|いしゃ|に|いく   # 「今日は医者に行く」
```

「libakaza は `は+医者` を `廃車` に誤結合する」と**コメントまで書いた**。しかし本 PR で `--explain` で実測したら、実際はこうだった:

```
変換候補 (flat, きょうはいしゃにいく):
  1. 今日歯医者に行く  score=96190   ← libakaza の選択
  2. 今日は医者に行く  score=95797
  差 = わずか 393
```

- libakaza は `廃車` ではなく **`歯医者`** を選んでいた (コメントも誤り)。
- そして **`今日歯医者に行く` は完全に正当な文**で、`はいしゃ` 単体も `歯医者 / 廃車` という実在語。むしろ `今日は医者に行く` より自然なくらい。
- つまり **「正解は は で切る」という当時の判断自体が、`歯医者` が正当な読みであることを確認せずに決めた推測**だった。

nuko-ime の開発規約 (CLAUDE.md) には、Golden Set の方針として **「複数解釈が成立する文は『誤り』と断定できないため収録しない (推測で正解を決めない)」** と自分で書いてあった。`きょうはいしゃにいく` は `今日は医者 / 今日歯医者` の両義で、**まさにこの方針に反する収録**だった。

→ **訂正**: `きょうはいしゃにいく` を Golden から除外。これはバグではなく正当な曖昧文であり、libakaza の選択 (`歯医者`) は妥当。

### この出来事の意味

評価基盤を作る目的は普通「対象 (変換器) の品質を測る」ことだ。だが実際には **最初に炙り出されたのは、テストを書いた人間 (＝私) の思い込み**だった。「誤分割のサンプル」として集めたものの中に、誤分割でないものが混ざっていた。

- 推測を「正解」としてテストに焼き込むと、**評価が対象をではなく思い込みを測る**ようになる。
- 特に「誤りの例」を集めるときほど危ない。確証バイアスで「これは誤りだ」という前提のラベルを、検証せずに付けてしまう。
- 防御策: **ラベルを付ける前に実データ (`--explain`) で確認する。両義文は入れない。** スコアの数値はテストで pin する (腐れば赤くなる)。

## 5. 残る難ケースの正体 — なぜ「直す」のが禁じ手か

### ケース A: `にわにはにわにわとりがいる` (庭には二羽鶏がいる)

```
予測: にわ|に|はにわ|にわとり|が|いる   = 庭に埴輪鶏がいる   score 93103
正解: にわ|に|は|にわ|にわとり|が|いる   = 庭には二羽鶏がいる score 92394
```

`は + にわ(二羽)` を `はにわ(埴輪)` に飲み込む。`埴輪鶏` は意味的にナンセンスだが、bigram のスコアでは勝つ (差 709)。**意味／長距離文脈**が要る領域で、単語 bigram では原理的に取りこぼす。

### ケース B: `すもももももももものうち` (李も桃も桃のうち)

```
予測: すもももももももものうち (1 文節、全くの未分割)  score 97129
正解: すもも|も|もも|も|もも|の|うち
```

全て `も` で構成された有名な早口言葉。曖昧性が極端で、libakaza は分割を諦める (全かなが最高スコア)。研究レベルの難問。

### なぜ「は を強制的に切る」ハックをやってはいけないか (実データ根拠)

一見、ケース A は「文中の `は` を切れば直る」と見える。だが実測が示すとおり:

```
はいしゃ → 廃車 / 歯医者 (は を切らないのが正しい、実在語)
はにわ   → 埴輪
ほか: はは(母) / はな(花) / はし(橋) / はなし(話) / はる(春) / は(歯) …
```

**`は` で始まる実在語は無数にある。** 「名詞の後の先頭 `は` を切る」ルールを入れると、これらが**全部 `は+○○` に崩壊**する。1 件の早口言葉を直すために、日常語を大量に壊す — これは nuko-ime の規約 **「個別対応は破綻する」** の典型。

→ **本当のレバーは言語モデルの質** (再訓練 / 語彙ブレンド / より長い文脈のモデル化)。これは進行中の [Mozc 語彙ブレンド](2026-11-22-mozc-vocab-blend-result.md) や再訓練の守備範囲であり、区切り評価 (`nuko eval --segment`) はその効果を before/after で測るための計器になる。

### 将来の選択肢: 「直す」でなく「選べるようにする」

強制せず、**segmented 変換で 2nd-best 以降の「文全体の別の区切り」を Space 候補として出す**設計はありうる (ATOK / Google 日本語入力がやっている「offer, don't force」)。ユーザーが `今日は医者` / `庭には二羽` を選べば、既存の文節位置学習がそれを覚える。非回帰だが IMK 境界 (`controller.rs`) に触るため実機 smoke 必須の中規模変更で、本件のスコープ外。

## 6. 方法論的まとめ

1. **2 軸分離**: 変換品質を「表層」と「区切り」に分けて測ると、誤りの原因が切り分けられる (今回: 区切りの誤りは過結合に一方向偏在、Precision 100%)。
2. **評価は対象だけでなく評価者も測る**: 「誤りの例」を集めるときほど、ラベルを実データで検証する。推測を正解に焼き込まない。
3. **数値は実行可能ドキュメントに**: スコアはコメントでなくテストで pin。両義文は Golden に入れない。
4. **難ケースの直し方は「層」で選ぶ**: 規則で直るもの=ルール、品質=モデル、個人=学習。早口言葉の過結合は**モデル層**の課題であって、個別パッチの対象ではない。
