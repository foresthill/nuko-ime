# コードとコメントの乖離を防ぐ（開発規律）

> **実装＝コード。コメントは実装の「意図(why)」を補うもので、実装そのものではない。**
> コメントがコードの事実（値・式）を複製すると、コードが変わったときコメントだけ取り残され、
> やがて**嘘をつくドキュメント**になる。このノートはその再発防止を開発レイヤーで共有するためのもの。
>
> 2026-11 の実インシデント（`engine.rs` のコメントが頻度スコアを `count*50` と記述していたが、
> 実コードは `count*10`）を起点にまとめた。

## 1. 何が起きたか（インシデント）

- `FrequencyEntry::score()`（`nuko-core/src/learning/frequency.rs`）の実体は
  `200_000 + count*10 − 減衰 + 追い越しboost`。
- ところが `engine.rs` の複数のコメントが `200_000 + count*50`、さらに
  「け×5=200_250」という**手計算した worked example**（×50 前提）を載せていた。
- `count*10` では `け×5 = 200_050`。コメントの数値も、それを前提にした説明も**嘘**になっていた。
- 実データ（`成功 学習×8 = 200080 = 200_000 + 8*10`）が `count*10` を裏付ける。

これは「些細なコメントの誤り」ではなく、**ドキュメント（コメント）が読み手を誤った実装理解へ導く**
アンチパターンそのもの。実際、このプロジェクトの別ドキュメントを書く際に、書き手がこの誤コメントを
信じて一度 `count*50` と書いてしまった（＝乖離が伝播した）。

## 2. なぜ起きるのか（根本原因）

| 根本原因 | 説明 |
|---|---|
| **コメントがコードの事実を複製していた** | 式・定数値をプロース（散文）で重複記述。真実の源(source of truth)が 2 つになり、片方（コード）だけ変わると他方（コメント）が取り残される。 |
| **プロースはコンパイラにもテストにも検査されない** | コードは型・テストで守られるが、コメントの数値主張は誰もチェックしない。変更時に**追従しなくても何も壊れない**＝静かに腐る。 |
| **手計算した worked example は特に脆い** | 「け×5=200_250」のような例は、式の値をコメント内に焼き込む。式が変わると例ごと嘘になる。 |
| **同じ数値が複数箇所に散っていた** | `count*50` / `200_250` が 3 箇所以上に重複。1 回の変更で全部を直す必要があり、漏れる。 |
| **変更時に数値を grep する習慣がなかった** | 乗数を `×50→×10` に変えたとき、コメント中の数値を探して追従しなかった。 |

一言でいうと: **「コードが知っている事実」をコメントに書き写したから。** 書き写した瞬間に二重管理が始まり、
同期は人間の注意力だけが頼りになる＝いずれ必ずずれる。

## 3. リーダブルコードでのコメントの位置づけ

『リーダブルコード』(Boswell & Foucher, 邦訳 オライリー) の該当章（5「コメントすべきことを知る」/
6「コメントは正確で簡潔に」）の要点:

- **コメントの目的は「書き手の意図を読み手に伝えること」**。コメント＝実装の代替ではない。
- **コードからすぐ分かることをコメントしない。** 式や値を言い換えただけのコメントは価値がマイナス
  （スペースを食い、かつ腐る）。→ 今回の `count*50` はまさにこれ。
- **「ひどいコード＋良いコメント」より「良いコード」。** コメントで補う前に、コードを自己説明的にする。
  例: マジックナンバーに名前を付け、コメントでなく**定数名**で意図を語らせる。
- **書くべきは「なぜ(why)」**。なぜこの設計か、なぜ他案を却下したか、定数の背景、ハマりどころ。
  **「何を(what)・いくつ(値)」はコードに語らせる。**
- コメントは**正確に**。あいまい・古い情報は無い方がマシ。

⇒ 本インシデントは「コードからすぐ分かる事実（式・値）をコメントに複製し、しかも不正確になった」＝
リーダブルコードが最も戒める型。

## 4. 再発防止策（開発レイヤー）

### 4.1 原則
1. **コメントに式・値を複製しない。真実の源はコード 1 箇所。**
   数値の背景を語りたいときは、**名前付き定数・関数を指す**（「`score()` 参照」「`DATETIME_SCORE`」）。
2. **数値の主張はテスト（実行可能ドキュメント）にする。**
   コメントは腐っても誰も気づかないが、**テストは腐れば赤くなる**。式や代表値を 1 本のテストで pin する。
3. **WHY を書き、WHAT/値はコードに語らせる**（リーダブルコード）。
4. **手計算の worked example を避ける。** どうしても例を示すなら、テストに書いて**実測値を使う**
   （手計算で焼き込まない）。

### 4.2 具体ルール（このリポジトリ）
- スコア式・boost・しきい値など**挙動を決める数値**は、`const` に名前を付けてコメントは定数定義の隣に 1 箇所だけ。
  他所のコメントからは**値を書かずに定数名で参照**する。
- 式を変えたら `grep -rnE "<その数値>"` でコメント/ドキュメント中の旧値を探して追従する（PR 前チェック）。
- 新しい「数値の約束」を導入したら、**公式を pin するテスト**を同じ PR で足す。
  例: [`frequency.rs::score_formula_is_pinned_count_times_10`](../nuko-core/src/learning/frequency.rs)
  （`count=1→200_010 / count=5→200_050` を assert。乗数を変えると赤くなる）。
- ドキュメント（`docs/`）がコードの数値を引くときは `file:line` を併記し、**実測または test で裏付ける**
  （[`RETYPE_CORRECTION.md` §5](RETYPE_CORRECTION.md) / [`LEARNING_ARCHITECTURE.md` §1.6 スコア透明化](LEARNING_ARCHITECTURE.md) と同方針）。

### 4.3 レビュー観点（チェックリスト）
各コメントに問う:
- [ ] このコメントは**コードから自明**か？ → ならば消す。
- [ ] **why（意図）**を語っているか？ → ならば残す価値がある。
- [ ] **式・値を含む**か？ → 定数名で参照するか、テストに移す。手計算の例なら消すか実測に置換。
- [ ] 同じ数値が**複数箇所**に書かれていないか？ → 1 箇所（定数/テスト）に集約。

## 5. まとめ

**コメントは実装ではない。** コメントにコードの事実を書き写した時点で二重管理が始まり、同期は人間の
注意力だけが頼りになる＝いずれずれる。だから「値・式はコードとテストに持たせ、コメントは why に徹する」。
これは『リーダブルコード』の「コードからすぐ分かることをコメントしない／良いコードはコメントに勝る」を、
このプロジェクトの**スコア透明化**（数値は実測・test で裏付ける）と接続した運用規律である。
