# フレーズ予測（履歴学習）設計 — #187

> 2026-11-12 設計相談の記録。実装前に方針を固めるための spike。
> 関連 issue: [#187](https://github.com/foresthill/nuko-ime/issues/187)
> 上位ビジョン: [`docs/FUTURE_FEATURES.md` §1 コンテクスト予測変換 / §2.2 ユーザー固有の傾向性](../FUTURE_FEATURES.md)
> 学習の思想: [`docs/LEARNING_ARCHITECTURE.md`](../LEARNING_ARCHITECTURE.md)

## 1. 背景（なぜやるか）

「ご確認いただけますと幸いです」のような**最頻出の定型句**が一発で変換できない、という報告が発端。

真因はバグではなく**ローマ字の「ん＋母音」綴り規則**（全IME共通）で、**語をまたぐ境界**（`ご確認`＋`いただけ` の `ん｜い`）では単一 `n` が `に` になり `にに` に化ける。

### 実機で裏取り済み（2026-11-12, ことえり ライブ変換ON）

| 打ち方 | ことえりの結果 |
|---|---|
| `gokakuninitadakemasuto`（単一n） | **互角に似ただけますと** ❌（nuko と同一） |
| `gokakuninnitadakemasuto`（二重n） | **ご確認いただけますと** ✅ |

→ **ライブ変換は境界を解消しない。** 既存IMEで「アポストロフィも文節変換もせず打てていた」のは、**予測変換（サジェスト）で全文を打ち切る前に候補を選んでいた**ため。つまり**予測こそが既存IMEの回避策の実体**。これを nuko にも入れるのが本設計。

ローマ字層では直せない（`ni→んい` にすると「に」が全部壊れる）。個別ハードコードもしない（規約「個別対応は破綻する」）。**唯一の正当な全体解がフレーズ予測。**

## 2. スコープ（相談で確定）

**v1 = 履歴学習のみ × Space変換時に候補へ混ぜる。**

### やること（v1）
- ユーザーが**文全体を確定**したら、その `読み(全体) → 表層(全体)` を**フレーズ**として記録（個人・常時ON）。
- **Space 変換時**、今の composition 読みを**前方一致**でフレーズストアに照会し、ヒットしたフレーズを**変換候補に追加**する。
- 例: 一度 `ご確認いただけますと幸いです` を確定 → 次回から `ごかくにん`（←末尾ん＝単一nで打てる）で Space を押すと候補に `ご確認いただけますと幸いです` が並ぶ。**ん＋母音境界に当たらない。**

### やらないこと（将来・別issue）
- seed 定型辞書の同梱（day-1 即効性。fast-follow 候補）。
- 打鍵中サジェスト（Space 前の自動表示）。UX 作り込みが要るので段階2。
- 文脈/段落/LLM ベースの予測（FUTURE_FEATURES §1.2–1.3）。
- community 配布・集合知（心の構造モデルの「集合的無意識」側）。

## 3. cold-start（正直に）

履歴学習なので**初回だけ**は正しいかなで一度打つ必要がある（`nn` / 文節変換 / 単語登録のいずれか）。
2回目以降は `ごかくにん` で永続的に回避できる。seed 辞書（将来）を足せば初回の摩擦も消える。
※ 既存の**単語登録**は実質「手動フレーズ登録」なので、初回の当座しのぎとして案内できる。

## 4. データモデル

### 4.1 フレーズストア（新規・常時ON・個人・非共有）
`~/Library/Application Support/nuko-ime/phrases.json`（人間可読・透明、Layer0 と同じ思想）

```jsonc
[
  { "reading": "ごかくにんいただけますとさいわいです",
    "surface": "ご確認いただけますと幸いです",
    "count": 3,
    "last_used": "2026-11-12T10:00:00Z" }   // recency は将来のスコアに使用（v1 は任意）
]
```

- キーは**全体読み**。照会は**前方一致**（prefix）。
- 個人データ。**共有しない**（[`LEARNING_ARCHITECTURE.md` §1.5 / プライバシー境界](../LEARNING_ARCHITECTURE.md)）。
- Layer0 `learning.json`（文節単位・完全一致）とは**別物**。混ぜない。

### 4.2 なぜ既存を流用しないか
- `learning.json`（Layer0）= 文節単位・完全一致。フレーズ（全体読み・前方一致）とは検索も粒度も違う → 分離。
- `observations.jsonl`（Layer1）= 全体 commit を既に記録しているが **opt-in**。フレーズ予測は常時ONにしたいので専用ストアを持つ（observations からの移行/初期化は将来検討）。

## 5. 記録トリガー（何を「フレーズ」とみなすか）

`commit`（確定）経路で、以下を**両方**満たすときフレーズとして記録:

1. **複数文節**の変換を確定した（＝文相当）。segmented 経路の whole-commit。
   - 単一文節・単語は Layer0 に任せる（フレーズにしない）。
2. 全体読みが**一定長以上**（例: 6〜8 かな以上。短すぎる定型を除外、閾値は要調整）。

- flat 経路でも「whole-reading の確定」が同条件を満たせば記録可（要検討）。
- 同一 `(reading, surface)` は count++。
- **過学習の轍を踏まない**（[[nuko-ime-learning-overgeneralization]] / PR #106）: フレーズは**完全一致の全体**のみ。接尾流用・分割流用はしない。

## 6. 予測トリガー & 表示（Space時に候補へ混ぜる）

composition の読み `R` で Space（最初の変換）時:

1. フレーズストアを `R` で**前方一致**照会（`reading.startsWith(R)`）。
2. ヒットを count 降順で上位 k 件、**変換候補リストに追加**する。
3. ランキング: **通常変換の1位は奪わない**方針で検討（予測は「候補の一つ」として見える位置に。暴発防止）。count が高い等で上位に出すかは要調整。スコア透明化（#183 `--explain`）と整合させ、予測候補は**出所が分かる**ようにする（将来 [[nuko-ime-candidate-source-badge]] の「予測」バッジ）。

### 重要な性質: 予測は「打った読みより長い表層」を確定する
`ごかくにん`（composition）を選ぶと `ご確認いただけますと幸いです`（より長い）が確定する＝**予測補完**。これは意図どおり。確定時に composition 全体を置換してフレーズを挿入する。

## 7. スコアリング / 透明性

- v1 は count（＋任意で recency）。FUTURE_FEATURES §2.3 の `α×頻度 + δ×recency` の素朴版。
- `nuko convert --explain`（#183）にフレーズ予測の内訳（出所=予測・count）も出せるようにする＝**誤爆や「なぜ出た/出ない」を推測でなく内訳で見る**（[[nuko-ime-scoring-transparency]]）。

## 8. ビルド順（bottom-up・各段で単体有用）

1. **PhraseStore** を nuko-core に新設: `reading→surface→count` ＋ 前方一致照会 ＋ `phrases.json` 永続化。
   - 検索は BTreeMap<reading, …> の range（prefix）or ソート Vec + 二分探索。フレーズは個人規模なので軽量で可。
   - 単体テスト（記録→prefix照会→count順）。
2. **CLI 配線**: `nuko predict <prefix>` を PhraseStore 参照に拡張（現状は静的辞書 prefix のみ）。`--release` で before/after を実測できる土台。
3. **記録フック**: commit（whole / segmented）経路で §5 の条件を満たすとき PhraseStore に記録。
4. **予測注入**: Space 変換時に §6 でフレーズ候補を候補リストへ。controller/engine の convert 経路に最小追加。
   - controller を触るので **実機 smoke test 必須**（打鍵・確定が壊れない、予測が暴発しない）。
5. （将来）seed 辞書 / 打鍵中サジェスト / community。

各段が単体で検証可能（1–2 は IME 不要、CLI で実測。3–4 は実機）。

## 9. 未決事項（実装前に詰める）

- 記録の閾値: 「複数文節」「全体読み ≥ N かな」の N（過剰記録 vs 取りこぼし）。
- 予測候補の**表示位置**（1位を奪うか・何件出すか）。暴発防止と発見性のバランス。
- flat 経路の whole-commit も記録対象にするか。
- recency を v1 に入れるか（入れるなら last_used の更新と減衰）。
- observations.jsonl（既存の全体記録）からの初期化を v1 でやるか将来か。
- 単語登録（手動フレーズ）とフレーズ学習（自動）の**重複排除/優先**。

## 10. 非機能・規約の確認

- プライバシー: フレーズは個人・端末内のみ・非共有（[[nuko-ime-mind-structure-layers]]）。
- 中間設計を避ける（規約「自動生成＋高頻度 human review を提案しない」）: 本設計は**完全自動の個人学習**（レビュー不要・冪等な count 更新）。seed は将来「配布（full-auto）」側。中間に落とさない。
- 個別ハードコード禁止: 特定フレーズを埋め込まない。あくまで**履歴からの一般機構**。
