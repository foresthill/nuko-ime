# 学習アーキテクチャ (かな→漢字の個人最適化)

ぬこIME の「使うほど自分に寄る / 寝てる間に賢くなる」学習機構の**実装できる具体アーキテクチャ**。

> **このドキュメントの位置づけ**
> - **なぜ / 倫理・戦略**: [`AI_AGENT_FOUNDATION.md`](AI_AGENT_FOUNDATION.md)(IME=個人AIエージェント論、諸刃の剣)
> - **フレームワーク(Stage 1-4)**: [`FUTURE_FEATURES.md` §8](FUTURE_FEATURES.md)
> - **本書**: 上記を「データモデル・データフロー・層の責務・ビルド順」に落としたもの
> - 合意した設計方針(2026-09-18、森岡さんと確認): 下から積む / churn-free dreaming / AI の役割は A→B 中心

## 0. 設計原則(不変・破ってはいけない)

1. **ローカル第一・デフォルト収集なし。** 何も集めないのが既定。外部送信は層ごとの明示オプトインのみ。
2. **完全オプトイン(層独立)。** Layer 1 を ON にしても Layer 3(AI)は別途同意が要る。デフォルト全 OFF(Layer 0 を除く)。
3. **透明性。** 学習データは**人間可読**(TOML/JSON)。ユーザーが閲覧・削除・エクスポート・インポートできる。
4. **churn-free dreaming。** dreaming は「提案を生成して人間がレビュー」ではなく、**履歴から個人重みを決定論的に再計算する**だけ。冪等・自動適用・溜まらない。
   → 過去の失敗(自動生成+高頻度human review が破綻)を繰り返さないための絶対条件。
5. **リアルタイム変換は既存の高速ロジック。AI は裏(バッチ)のみ。** 変換のたびに API を叩かない。

## 1. 層構成

```
Layer 0  頻度学習            確定候補の頻度を即時記録 → 変換順位に反映     ✅ 実装済
Layer 1  観察ログ            「入力→emit→(ユーザーが直した)」を記録        ⬜ 未 (次に着手)
Layer 2  訂正学習            観察ログから確定的な訂正/選好を抽出 → 変換へ   ⬜ 未
Layer 3  AI dreaming (BYOK)  Layer 1-2 のデータを AI が最適化(バッチ・オプトイン) ⬜ 未
```

**ボトムアップの理由**: Layer 3 の AI は「材料(Layer 1-2 のデータ)」が無いと何も学習できない。Layer 1-2 は AI 無し・プライバシーリスク無しで**単体で有用**。だから下から作る。

### 各層の責務

| 層 | 入力 | 出力 | データ | オプトイン | AI |
|---|---|---|---|---|---|
| **0 頻度** | 確定候補 | 頻度スコア | `learning.json` | (常時ON、既存) | ✗ |
| **1 観察** | 入力/emit/訂正イベント | 観察ログ | `observations.jsonl` | 要 (デフォOFF) | ✗ |
| **2 訂正学習** | 観察ログ | 訂正ルール/選好重み | `corrections.toml` | Layer 1 と連動 | ✗ |
| **3 AI dreaming** | Layer 1-2 データ | 再計算した重み | Layer 2 データを更新 | **別途要** (デフォOFF) | BYOK |

> 実装状況 (2026-11): 上の「未」は初期計画時点の表記。現在は **Layer 0-2 稼働**
> (`observations.jsonl` のオプトイン記録 → `auto_relearn` で `corrections.toml` に即反映)、
> **Layer 3 は nuko-cli に実プロバイダの芽** (`nuko dream --provider`) がある。

## 1.5 心の構造との対応（設計思想）

森岡さんの構想 (2026-11-08)。学習の層は**心の構造のメタファ**に対応づく。単なる比喩でなく、
「何を共有し／何を個人に留め／何を推論に委ねるか」の**設計指針**になる。

| 心の層 | ぬこIME の機構 | 共有範囲 | 実体 |
|--------|---------------|---------|------|
| **意識** | いまの変換セッション（composition・候補列・ユーザーの選択） | — (揮発) | runtime state |
| **個人的無意識** | Layer 0-2 個人学習（頻度 / 訂正 / 文節位置 / ユーザー辞書） | **共有しない**（ローカル第一・個人に留める） | `learning.json` / `corrections.toml` / `segmentations.toml` / `user_dict.json` |
| **集合的無意識** | 配布モデル（SKK-JISYO.akaza + ngram）＋ 将来のコミュニティ辞書（opt-in・匿名集約・curation） | **みんなに有益な分だけ共有**（アップデートで配布） | `model-pipeline` 成果物 / コミュニティ辞書 (構想) |
| **超意識** | Layer 3 AI dreaming（頻度を数えるのでなく「意図」を推論して個人重みを再計算） | 個人内（BYOK）。集合から創発したパターンの curation は集合へ還す | nuko-cli `nuko dream --provider` (芽) |

**設計指針として読む**:

- **個人 vs 集合の分離は必須。** 個人的無意識（個人学習）は決して集合に漏らさない（§5 プライバシー境界・マスキング前提）。集合的無意識へ上げるのは「誰にとっても有益な一般語・固有名の揺れ」だけで、**curation gate** を通す。「個別の学習は共有しない／有益なものだけアップデートで配布」という方針そのもの。
- **超意識 ＝ 意図推論。** 頻度（個人的無意識）でも統計（集合的無意識）でもなく、「`しんに` と打ったが真意だろう」と**理解して補う**層。形而上的な意味での超意識そのものは工学の対象外だが、その**機能的な影** ＝ LLM による意図推論・生成（dreaming）は実装可能で、芽は既にある。*変換の瞬間に*意図推論を効かせる（リアルタイム意味判断）のは未実装の研究領域。
- この対応は VISION の「**和多志**」（個を保ちつつ全体に還す）と一貫する。[`VISION.md`](VISION.md)

## 1.6 スコア透明化 → AI 介入の足場（設計思想）

森岡さんの構想 (2026-11-12)。**「なぜこの候補が1位なのか」を人が読めるようにする**ことを、
学習機構の一等の設計目標に置く。単なるデバッグ機能ではなく、ツールの価値と AI 介入の前提になる。

**なぜ透明化が核心か**:

- **変換は決定論。順位は必ずスコアの大小で説明できる** — ブラックボックスにする理由がない。
  説明できないなら、それは「理解していないまま動かしている」サインで、推測で直す羽目になる。
- **ユーザーが「学習が効かない」と感じる場面の多くは、実は正しく count 順に効いている**
  （例: `そこ(×27)` より `底(×28)` が上 ＝ 確定回数どおり）。内訳が見えて初めて、
  「バグ」なのか「データどおりの正当な結果」なのかを切り分けられる。
- **透明化は AI 介入の足場になる。** スコアの内訳（libakaza 基礎 / Layer0 頻度 / Layer2 選好）が
  構造化されていれば、超意識（Layer 3 dreaming）が「どの重みをどう研ぎ直すか」を**根拠つきで**
  提案・再計算できる。見えないものは AI にも渡せない。

**実装の芽**: `nuko convert --explain`（PR #183）が、文節ごとの候補を
`score / source(libakaza・個人・学習辞書) / 学習×N` に分解して表示する。これにより
「ように→用に 回帰」の真因（下記 §個人重みの合成の add/max 非対称）を**推測でなく実測で**特定できた。

**候補パネルでの可視化が実現（2026-11-14, v0.1.12）**: `--explain` は CLI だけだったが、
IME の候補ウィンドウ上でスコア・出所を見られるようにした（いずれも既定 OFF の opt-in、
**表示専用で変換結果・順位は不変**）。
- **スコア可視化**（PR #196）: 各候補行に変換スコアを併記。
- **スコア美化**（PR #197）: 小さい等幅数字 + **正=緑 / 負=オレンジ**。色そのものに
  「値が大きい=緑=優先」を語らせる。
- **出所バッジ**（PR #188）: 自分由来の候補にだけ「学習 / 個人」、エンジン既定は無印。
- 実装上の要点は CLAUDE.md 落とし穴 #11（併記は表層文字列に混ぜず、別経路＋utf16範囲記録 →
  `addAttributes_range`）。

**可視化が開く 3 方向（森岡さん 2026-11-14「スコア可視化は明暗だった」）**: スコアが
*見える* ようになったことは、次の設計の軸を 3 つ開いた。

1. **AI 連動性の一段アップ** — スコアという共通の数値基盤ができたので、超意識（Layer 3
   dreaming）に「どの候補をどれだけ上げ下げするか」を**根拠つきで**提案・適用させられる。
   「AI にどう直してもらうか / アップデートしてもらうか」が具体化する。*見えないものは
   AI にも渡せない* の実装的裏付け。
2. **ゲーミフィケーション / RPG 性** — 「選ぶほどスコアが育つ」が経験値のように見え、
   変換を“育てる”動機づけになる。透明化はモチベーション装置でもある
   （出所バッジの「学習 ×N」回数表示＝将来の芽と地続き）。
3. **調整 UI の前提** — だから「スコアの上げ幅（Layer0 BOOST 量）をユーザーが設定可能に
   する」案が意味を持つ。見える → いじれる、の自然な次段。

これらは本アーキテクチャの核（学習4層 ↔ 心の構造、超意識＝意図推論）と噛み合う。
①AI連動 × ②ゲーミフィケーション を次段の設計主軸とする。

### 学習の「強さ」を設定可能に + 追い越し（恒久・単調）— 2026-11-14 決定

可視化で実機検証したところ、**1回選択でスコアが +10 しか上がらない**ことが分かった
（`様` 200208 → 200220）。式は `frequency.rs::score()`：

```
score = 200_000 (BOOST) + 使用回数 × 10 − 時間減衰(最大30)
```

1 選択 = `+10`。すでに高スコアの rival（例 `用` ≈ 294,329）がいると、差を埋めるのに
**約 9,400 回**選ぶ必要があり、実質的に追いつけない。「選んだのに上がった気がしない」。

**方式の検討と判断**:

| 方式 | 1回で逆転 | 単調（下がらない） | UX |
|---|---|---|---|
| A. 係数を設定可能に（`×10 → ×N`） | 差が大きいと不可 | ✅ | 予測しやすい |
| B. 直近選択ボーナス（減衰 recency） | ✅ | ❌ | **「さっき上に出たのに戻ってる!?」= 混乱** |
| **A + 追い越し（恒久・単調）** ← 採用 | ✅ | ✅ | 納得感が高い |

- **B（減衰する recency ボーナス）は採用しない。** 非単調（上がって下がる）動きは、
  スコアが見えていても「なぜ順位が戻ったのか」というユーザーの混乱を生む（森岡さん指摘）。
- **採用 = 「選んだら今のトップより上へ恒久的に引き上げる」（追い越し）。** スコアは
  **選択時だけ上がる＝単調**。勝手に下がらないので「戻った!?」が起きず、可視化との相性もよい
  （数字が上がる一方で納得できる）。「1回で逆転」と「戻らない」を両立する。
- **ユーザー設定可能**（弱 / 中 / 強）。「ドラスティックに上げたい」人と「少しずつでいい」人の
  両方を吸収する。弱 = 現状の `×10`、強 = 1 選択で即トップ級。**既定は強**
  （初期ユーザーの要望。設定で下げられる）。
- 実装は `frequency.rs` のスコア計算（純粋関数・テスト付き）を中心に、追い越しは学習記録時に
  同一読みの rival 最大スコアを見て決める。before/after はスコア可視化で実測する。

**運用原則**（グローバル規約「推測を断定的に語らない」と一体）:

1. **誤変換を見たら、まず `--explain` で内訳を撮る。** 推測で辞書に足したりスコアを弄らない。
2. **`--explain` で見つけた実データの失敗ケースは、そのままユニットテストに落とす。**
   「透明化 → 失敗の再現 → テスト固定」で回帰を恒久ガードにする
   （例: `segment_frequency_high_count_existing_beats_low_count_injection`）。
3. **スコア設計を変えるときは before/after を `--explain`・実データ・`--release` で実測してから出す。**

## 2. データモデル(人間可読・透明)

### Layer 0: 頻度 (既存 `learning.json`)

現状: `HashMap<reading, Vec<FrequencyEntry{ surface, reading, count, ... }>>`。
`LearningManager::record()` が確定時に `increment()`。**context は現在未使用**(`_context`)→ Layer 2 で活用する。

### Layer 1: 観察ログ `observations.jsonl` (追記のみ、1行1イベント)

```jsonc
{"ts":"2026-09-18T14:30:05Z","kind":"commit","reading":"はんい","surface":"範囲","cands":["繁位","範囲"],"picked":1}
{"ts":"2026-09-18T14:31:10Z","kind":"correction","reading":"こんばん","emitted":"今晩","corrected":"こんばん"}
```

- `kind`: `commit`(確定) / `correction`(直後に直した) / `romaji`(誤変換報告など)
- 追記のみ・ローカルのみ。ローテーション(サイズ上限)あり。
- **これが Layer 2/3 の唯一の入力源**。オプトインで初めて書き出す。

### Layer 2: 訂正・選好 `corrections.toml` (人間可読・編集可)

```toml
# 「いつも X を Y に直す」= 確定的な個人ルール (信頼度しきい値を超えたもの)
[[preference]]
reading = "こんばん"
prefer = "こんばん"     # 「今晩」より「こんばん」を上位に
weight = 8
seen = 12               # 観測回数 (透明性)

[[context_bias]]        # 文脈依存の選好 (Layer 0 の context 未使用分を補う)
reading = "きしゃ"
prefer = "記者"
after = "新聞"          # 「新聞」の後なら「記者」
weight = 5
```

- 頻度(Layer 0)だけでは拾えない「文脈」「訂正」を確定ルール化。
- **誤訂正の偶発学習を排除**: 信頼度しきい値(`seen` 回数・一貫性)を超えたものだけ昇格(FUTURE_FEATURES §5.4)。
- ユーザーが直接編集・削除可能(透明性)。

### 個人重みの合成

変換時の候補スコア = `libakaza/辞書スコア` + `Layer0 頻度` + `Layer2 選好/文脈バイアス`。
すべてローカル・決定論的。AI はこの `Layer2` を**再計算する**だけで、変換パスに AI は挟まない。

#### ★ 不変条件: 学習は **flat / segmented の両経路** に適用する

変換には 2 つの経路がある。**両方に同じ個人重みを効かせること** — 片方だけだと「文中の語が永遠に学習に勝てない」バグになる。

| 経路 | 使われる場面 | 実装 (`engine.rs`) |
|---|---|---|
| **flat** `convert()` | 単文節・静的辞書フォールバック | Layer0/Layer2 を関数内で合成 |
| **segmented** `convert_segmented()` | libakaza による複数文節（＝**文の大半**） | `apply_segment_corrections`(L2) ＋ `apply_segment_frequency`(L0) を**文節ごとに**適用 |

#### ★ 不変条件: segmented の Layer0 反映は「加算」でなく **`max(基礎, Layer0)`**

`apply_segment_frequency` が Layer0 頻度を候補へ効かせるとき、**既存候補も注入候補も「純 Layer0 スコア」に揃える**（`c.score = c.score.max(lc.score)`）。加算にしてはいけない。

- **なぜ**（2026-11-12、`--explain` で実測して判明した「ように→用に」回帰の根治）:
  libakaza の文節候補スコアは**ログ確率ベースで多くは負値**。既存候補に `基礎 + Layer0` と**加算**すると、
  負の基礎に沈んだ高 count 表層が、候補に無く**純 Layer0** で注入される低 count 表層に**逆転**される。

  | 読み `ように` | BEFORE 加算 | AFTER max |
  |---|---|---|
  | ように (学習×36) | `-1408 + 200360 = 198952` → 2位 | `max(-1408, 200360) = 200360` → **1位** |
  | 用に (学習×4・注入) | 純 `200040` → **1位** | 純 `200040` → 3位 |

- `max` にすると学習表層が**純 Layer0 で count 順**（36>5>4）に並ぶ。基礎が学習より高い稀なケース（強い libakaza 候補）は `max` が基礎を残すので回帰しない。
- flat `convert()` 側は元々「libakaza 候補へ Layer0 を注入（置換）」で正しく count 順。壊れていたのは segmented だけだった。

- **Layer 0 頻度は opt-in 不要の常時 ON**。だが `convert_segmented` は当初これを参照しておらず、Layer 2（観察ログ **opt-in** 前提）だけを適用していた。結果、観察ログ未有効ユーザーでは**文中に現れる語**に学習が一つも効かず、`ほう→法`・`よう→用` のような libakaza 既定が永遠に 1 位に戻った（2026-11 報告「砲→方 / 用→様 が何度直しても勝てない」、PR #178 で `apply_segment_frequency` を追加して根治）。
- **教訓**: 学習層を増やす・変換経路を分けるときは、**新経路にも全層を配線したか**を必ず確認する。片系統だけの適用は「単体では直るが文中では直らない」という再現しにくいバグを生む。
- segmented 側の学習適用は **読み完全一致のみ**（接尾・分割への流用はしない）。流用は常用語を壊す（→ 後述の over-generalization、`correction.rs` の 2026-09-29 回帰）。

> 残件（③ 降格 / 文脈）: `max` で count 順には正しく並ぶが、**count が拮抗する誤学習は居座る**。
> 例 `そこ`: `底(×28) > そこ(×27)` は確定回数どおりの**正当な結果**で、ユーザーが「そこ」を望んでも
> `max` では覆らない（`そこも` も文節 `そこ`+`も` に割れ同型）。これを覆すには 2 方向:
> (a) **打ち直し＝間違い側を降格** する決定的機構（count 上限・対数・訂正時デクリメント等）、
> (b) **文脈**（`context_hash` は現状どこも null。前文節・後続で選好を変える）。
> どちらも「確かなロジックが見えてから」着手する研究項目。スコア透明化（§1.6）と AI 介入（超意識）の接続先。

## 3. データフロー

```mermaid
flowchart TD
  K[打鍵/確定] -->|即時| L0[Layer0 頻度 +1]
  K -->|オプトインON| L1[Layer1 観察ログ 追記]
  subgraph リアルタイム変換 (高速・AI無し)
    C[かな] --> S[候補スコア合成]
    L0 --> S
    L2[(Layer2 訂正/選好)] --> S
    S --> R[候補提示]
  end
  subgraph バッチ (裏・任意)
    L1 --> E[Layer2 抽出: しきい値超えを昇格]
    E --> L2
    L1 -.->|Layer3 ON時のみ| AI[AI dreaming: 再計算]
    L2 -.-> AI
    AI -.->|決定論的に上書き| L2
  end
```

要点: **リアルタイム経路に AI は無い**。AI は「バッチで Layer2 を研ぎ直す」だけ。だから速度・プライバシー・churn-free を同時に満たす。

## 4. Layer 3 — AI dreaming (BYOK) の詳細

### いつ走るか(§8.4 の論点)
- **手動 / 充電中 / 夜間バッチ**から選択。デフォルトは**手動 or 充電中**(バッテリー配慮)。
- 常駐しない。1回のバッチで完結する冪等処理。

### 何を渡し / 何を受け取り / どう適用するか(churn-free の担保)

| | 内容 |
|---|---|
| **入力(AIへ)** | Layer1 観察ログ + Layer2 現行ルール(**ローカルデータのみ**。オプトインで送信先=BYOK プロバイダ) |
| **AIの仕事** | 「訂正パターンの一般化・整理・重み再計算」= 役割 A→B。**新しい提案の生成ではない** |
| **出力(AIから)** | 再計算された Layer2(訂正/選好/重み)**そのもの** |
| **適用** | Layer2 を**丸ごと決定論的に置換**(差分レビュー無し)。前回結果との diff はユーザーが見られる(透明性)が、承認は不要 |

→ **提案キューを作らない**。出力は常に「完全な Layer2」であり、溜まらない。気に入らなければ Layer3 を OFF にすれば Layer2 は Layer1 からの決定論的抽出に戻る。

### BYOK(§8.5)
- プロバイダ抽象: Anthropic / Gemini / OpenAI / ローカル LLM(Ollama/llama.cpp) / **none**。
- 設定: `~/.config/nuko-ime/ai.toml`(プロバイダ・モデル・トリガ)。**API キーは環境変数経由**、本体に保存しない。
- デフォルト OFF。ON にする画面で「何を・どの AI に・いつ渡すか」を明示(AI_AGENT_FOUNDATION §4.5)。

## 5. プライバシー境界

```
[ローカルのみ・常時]        Layer 0 頻度
[ローカルのみ・オプトイン]  Layer 1 観察ログ / Layer 2 訂正学習
[外部送信・別オプトイン]    Layer 3 で BYOK プロバイダに Layer1-2 を渡すとき (ローカル LLM 選択なら外部送信ゼロ)
```

- 何も設定しなければ Layer 0 のみ = 従来通り、収集ゼロ。
- Layer 3 で**ローカル LLM(Ollama)を選べば、AI 学習でも外部送信ゼロ**。これが最もプライバシー厳格な構成。

## 6. ビルド順(bottom-up・各段で単体有用)

| Phase | 内容 | 完了判定 |
|---|---|---|
| **A. Layer 1 (観察ログ)** | オプトイン設定 + commit/correction イベントを `observations.jsonl` に追記 + 閲覧/削除 | ON にすると自分の入力履歴がローカルに貯まり、見られる |
| **B. Layer 2 (訂正学習)** | 観察ログ → しきい値抽出 → `corrections.toml` → 変換スコアに合成。record() の context 活用 | 「いつも直す変換」が次から最初から正しく出る(AI 無しで) |
| **C. Layer 3 (AI dreaming)** | `ai.toml` + プロバイダ抽象 + バッチ再計算 + 適用 + diff 可視化 | AI を設定すると dreaming 後に変換選好が研がれる。OFF で Layer2 決定論に戻る |

**まず Phase A から**。ここで初めて「AI に食わせるデータ」が生まれる。

## 7. 未決事項(実装前に詰める)
