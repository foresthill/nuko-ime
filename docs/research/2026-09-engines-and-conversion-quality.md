# 変換エンジンと候補品質の調査レポート (2026-09)

ドッグフーディングで浮上した「候補が少ない / 名前・複合語が正しく割れない」問題の
技術的背景と、選択肢（libakaza を育てる / mozc / フルモデル）を整理する。

> 一次ソース: [google/mozc](https://github.com/google/mozc)、本リポジトリの `model-pipeline/`、
> [Google Japanese Input (Wikipedia)](https://en.wikipedia.org/wiki/Google_Japanese_Input)

## 1. なぜ「候補が少ない」のか（根本）

**辞書は十分大きい**。`SKK-JISYO.akaza` は **約 105 万エントリ**あり、`予`・`与` 等の
一般的な漢字も入っている。それでも候補に出ないのは、**言語モデル（unigram/bigram）が
`min` プロファイルで訓練されている**ため。

| プロファイル | epochs (MAY/SHOULD/MUST) | 訓練時間 | ランキング品質 |
|---|---|---|---|
| **min**（現行リリース） | 2 / 5 / 50 | 数分 | 粗い（良候補が上位9件に埋もれる） |
| **full** | 大幅増（最大 10000） | 数十分〜数時間 | 精密 |

`min` は確率推定が甘く、`よ→予` のように**辞書にはあるが上位に出ない**候補が多発する。
静的辞書の補完（`よ→予`、`よしゅく→予祝` 等）は**個別の穴埋め**で、根本ではない。

### B. フルモデル訓練のプロセス（結果は出るか）

出る。手順と各段の意味：

1. `cd model-pipeline && make all PROFILE=full`
   - **コーパス整形**: Wikipedia + 青空文庫 + CC-100 を分かち書き・頻度集計
   - **辞書生成**: `SKK-JISYO.akaza`（surface/yomi/cost）
   - **言語モデル訓練**: unigram/bigram/skip-bigram の cost を epochs 分反復学習
     （ここが min→full で大きく変わる。cost が実頻度に近づき、k-best 順位が改善）
2. 反映: 生成された 6 ファイルを `~/Library/Application Support/nuko-ime/akaza-model/` に
   `cp` して `killall NukoIME`（`install.sh` は不要 = モデルは Rust コードと別物）
3. 体感: 「候補が少ない」「名前の誤変換」が**全体的に**改善する見込み

**注意**: full は**ディスクを数 GB 使う**。現在 15Gi 空き（97%）とタイトなので、
`cargo clean` 等で空けてから走らせる。完了後は**新モデルとして再リリース**（配布物更新）。

## 2. エンジンの選択肢

### 2-a. libakaza（現行 = Path B）
- **Rust 実装、MIT**。nuko に自然に統合できる（現行採用）
- 品質は**モデル訓練しだい**（上記 min→full で伸びる）
- 弱点: 分割（segmentation）が名前・複合語で崩れやすい（→ §3 の A で補う）

### 2-b. mozc（Google 製 OSS）
- **BSD 3-Clause**（Google のコード。`src/third_party` は各ライセンス）。nuko の Apache/MIT と互換
- **成熟していて変換品質が高い**。Linux（ibus-mozc / fcitx-mozc）・macOS・Windows で実績
- ただし:
  - **C++ 実装**。Rust の nuko にエンジンごと差し替えるのは**大工事**（FFI 境界・ビルド）
  - OSS 版の辞書は **Google 日本語入力の社内完全版より小さい**（それでも実用十分）
- **既に部分利用**: nuko のローマ字テーブルは mozc 由来（`MOZC_TABLE`）

### 2-c. 判断（正直に）
- 「最初から mozc で良かったのでは」という問いは妥当。**mozc で満足するユーザーもいる**
- ただし現状 libakaza でここまで作り込み、**Rust で完結する保守性**の利点は大きい
- **当面は libakaza を育てる**（full モデル + 分割学習）。mozc エンジン統合は
  「品質が頭打ちになったら検討する将来の大選択肢」として保持

## 3. 分割の弱点と対策（A: 分割境界の学習）

libakaza は名前・複合語を誤分割する（実測）:
- `ざびさん…` → `[ざ][びさん]`（欲しいのは `[ざび][さん]`）
- `よしゅく` → `[よ][しゅく]`（欲しいのは `[よしゅく]`=予祝）

**単体**は「読み全体に辞書の語 / 学習があれば flat 優先」で対処済み（`has_dict_word` /
`has_whole_correction`、PR #97/#104）。**文中**（`ざびさんと大阪に…`）はまだ。

**A の設計**: 学習した読み（`ざび`）・辞書の語を**分割境界のヒント**として使う。
文中に `ざび` が現れ、かつ自然分割で 1 文節になっていなければ、
`convert_segmented_forced` でそこを**強制境界**にする（内部の自然境界を除去、
前後は自然分割）。これが「**文節の切り方の学習**」の実装。

## 4. 【実測】フルモデル訓練の結果（2026-09-30）

B（`make all PROFILE=full`, **epochs=10000**）を実行し、生成した 6 ファイルを実機に反映。
**候補品質が全体的に一段上がった**。min では壊れていた常用語が、**個人学習に頼らず
素のモデルで正しく 1 位**になる（`corrections_applied=false` = 学習ではなくモデルの力）。

| 入力 | min モデル | **full モデル** | 学習依存 |
|---|---|---|---|
| たいかく | た以下く | **体格** | なし (`corrections_applied=false`) |
| せいかつ | 背以下つ | **生活** | なし |
| だいじょうぶ | 台じょうぶ | **大丈夫** | — |
| めーるしておきましただいじょうぶです | …台じょうぶ | **メールしておきました大丈夫です** | — |
| じかんなるとき | — | 時間あるとき | — |

### 何をしたのか（技術的な中身）

`learn-corpus` が、curated コーパス（`training-corpus/{must,should,may}.txt`）と
Wikipedia/青空文庫/CC-100 由来の頻度統計（`work/stats-*.trie`）から、
**n-gram 言語モデル（unigram / bigram / skip-bigram）の cost を反復学習**する。

- **cost** = 「この読み→表層／この語の並び」の尤もらしさ。低いほど良い候補。
- **epochs** = cost を実頻度に合わせて磨く反復回数。min=50 → **full=10000**（MUST 層）。
  反復が増えるほど cost が実際の日本語頻度に近づき、**k-best（候補順位）が精密**になる。
- min は確率推定が甘く「大丈夫」が候補にあっても 3 位に埋もれる。full は 1 位に出る。

生成物（6 ファイル、`~/Library/Application Support/nuko-ime/akaza-model/` に配置）:
`SKK-JISYO.akaza`（辞書 ~105 万語）/ `unigram.model` / `bigram.model(.scores)` /
`skip_bigram.model(.scores)`。**Rust コードとは独立**（`install.sh` 不要、`cp`+`killall` のみ）。

実行時間: 本機で約 10 分（epochs=10000）。当初「数時間」と見積もったが、curated コーパスが
コンパクトなため実測は短かった。ディスクは corpus-stats(~270MB)+UniDic を含め数 GB。

> ロールバック用に min モデルを `akaza-model.min-backup/` に退避してある。

### mozc と比べて（2026-09-30 追記）

「最初から mozc なら苦労はなかったか」への実測を踏まえた答え:
- **変換品質の弱さ**（候補が少ない等）は libakaza の min 未訓練が主因で、フルモデルで
  実用域に到達。mozc は最初から高品質だが、フルモデルで差は縮まった。
- 一方 2026-09 の**回帰（体格→た以下く / 大丈夫→台じょうぶ）は nuko 独自の学習層の
  バグ**で、エンジン非依存。mozc でも学習層は自作するため同種のリスクは残る。
- 結論は §2 のまま: **当面 libakaza を育てる**。nuko の存在意義は AI 学習層（Rust で書く）で、
  mozc（C++）の採用は差別化の本体を作りやすくはしない。品質頭打ち時に統合を再評価。
