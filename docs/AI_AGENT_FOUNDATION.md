# ぬこIME as Personal AI Agent Foundation

**個人 AI エージェントの基盤としての日本語 IME**

最終更新: 2026-05-25

---

## このドキュメントの位置づけ

[FUTURE_FEATURES.md](FUTURE_FEATURES.md) の Section 8 (AI 駆動の自己学習機構) は、
ぬこIME 自体が賢くなる仕組みを論じる。本ドキュメントはその一歩先、
**「IME が捕捉するテキストデータは、IME の精度向上だけでなく、
ユーザー個人の AI エージェントの基盤データになり得る」** という戦略的観察を文書化する。

これは features ではなく **thesis (思想)** である。ぬこIME がなぜローカル
OSS でなければならないのか、そして「日本語ユーザー」という制約が
なぜ強みに変わり得るのかを論証する。

> 戦略的主張を含むため、断定調を避け「〜の可能性がある」「〜と考えられる」と
> 表現する。実装判断の根拠とする際は、各節の根拠の強さを各自評価すること。

## 1. 起点となる観察

日本語ユーザーがコンピュータに文字を入力する行為は、英語ユーザーのそれと
構造的に異なる。

- 英語: キーボード入力 → 直接画面に表示 (1 ステップ)
- 日本語: キーボード入力 → **IME による変換** → 画面に表示 (2 ステップ)

この **2 ステップ目の存在** が、日本語ユーザー固有の情報レイヤーを生み出す。

### 1.1 IME が暗黙的に保持する情報

IME は変換のために、以下を不可避的に処理する:

| 情報 | 例 |
|---|---|
| 読み (かな) | `こんにちは` |
| 変換結果 (確定文字列) | `こんにちは` (ひらがな確定) / `今日は` (誤変換) |
| 変換候補の選択履歴 | 第 1 候補 / 第 N 候補 / 訂正 / 再変換 |
| タイミング | いつ打ったか、どれくらい考えてから確定したか |
| 文脈 | 直前の文・段落 |

これは **IME が動く以上、必ず通過する情報** である。
通常の IME はこれを変換精度向上のためだけに使い、入力後すぐ破棄する。

ぬこIME (Section 8.6 のログ設計) は、**ユーザー同意の上でこの情報を保持する**。

## 2. 海外圏との構造的非対称性

ここがこのドキュメントの核となる観察である。

### 2.1 個人 AI エージェントへの「自己情報供給」の構造

LLM ベースの AI エージェント (ChatGPT, Claude, Gemini 等) が個別ユーザーに
寄り添うには、そのユーザーに関する情報を必要とする。供給経路を比較する:

| 経路 | 必要な意識 | データ量 | 真正性 |
|---|---|---|---|
| 明示的なプロンプト ("私は〇〇です") | 高 (意識的に話す必要あり) | 少 | 高 (本人が選んで開示) |
| Memory 機能 (ChatGPT 等) への登録 | 高 (意識的に保存する必要あり) | 中 | 中 (記憶として選別された情報) |
| エージェントへの逐次対話 | 中 (会話中の言及) | 中〜大 | 中 (対 AI 用に整形されがち) |
| **IME 経由の日常入力 (本提案)** | **低 (打つだけ)** | **大** | **高 (普段の自分そのもの)** |

英語圏ユーザーは IME を使わない。
**自己情報を AI に供給するには「意識的に話す」しか経路がない**。

日本語ユーザーは IME を経由するため、**「日々打つ」という無意識的行為そのものが
自己情報の供給になり得る** (ぬこIME がそれを構造化して保持する場合)。

### 2.2 非対称性の意味

これは技術選択の差ではなく、**言語と入力方式に由来する構造的非対称性** である。
中国語ピンイン入力、韓国語ハングル入力にも同種の構造があるが、本ドキュメントは
日本語ユーザーを主対象とする。

ぬこIME は、この構造を **積極的に資源化する** 設計を取り得る数少ない
プロジェクトの一つである。なぜなら:

- 大企業 IME (Apple, Google, Microsoft, ATOK) は、データを集約しても
  プライバシー上ユーザーに返せない / 学習に使えない
- 個人 OSS でなければ、**「ユーザーの手元に置いたまま AI に渡す」設計が成立しない**

## 3. 価値提案: 無意識的レイヤーから AI へ

### 3.1 「思考のログ」としての入力データ

ユーザーが 1 日に打つテキストは、その人の:

- **語彙** (どの単語を、どのくらいの頻度で使うか)
- **文体** (語尾、句読点、改行の癖、長さ)
- **関心領域** (技術 / ビジネス / 創作 / 私信)
- **思考のパターン** (主張型 / 説明型 / 物語型)
- **修正の癖** (どこで迷うか、何を打ち直すか)

を含む。これは個人プロフィールとして極めて高密度であり、かつ
**普段の自分そのもの** (対 AI 用に整形されていない真正のテキスト) である。

### 3.2 AI エージェントが「自分に寄っていく」とはどういうことか

このログを (BYOK で設定された) AI バックエンドに供給した場合、以下が可能になる:

| 機能 | 効果 |
|---|---|
| プロンプト時の自動文脈付与 | "あなたは〇〇な文体を持つ" を毎回書かなくて済む |
| 文体模倣 | エージェントが書く文章が「自分が書いたっぽい」になる |
| 関心領域への共鳴 | 質問への答えが、自分が普段使う比喩や前提を含む |
| 個人辞書 / 略語の理解 | "あれ" "例の件" 等の暗黙参照が通じる |
| 時間軸的記憶 | 過去に書いたテーマを参照できる (本人の許可下で) |

これは ChatGPT Memory 等の既存機能の **拡張ではなく、ベースレイヤー** である。
既存機能はユーザーが意識的に登録した情報を扱うが、ぬこIME 由来の情報は
ユーザーの普段の入力そのものから抽出される。

### 3.3 なぜこれが「エージェント」と呼ぶに値するか

エージェント (代理) という言葉の本来の意味は、「本人の代わりに考え、行動する」
存在である。代理が成立するには、本人を **十分に理解** している必要がある。

普段の入力データを基盤に持つ AI は、対話だけを情報源とする AI より、
代理としての精度が原理的に高くなり得る。

## 4. 諸刃の剣 — 明示的に書くべき影

このセクションは、ユーザー自身が指摘した点である。**価値提案と表裏一体の
リスクを正直に文書化する** ことが、誠実な設計の前提となる。

### 4.1 入力が偏ればエージェントも偏る

- ネガティブな表現ばかり打つ人の AI エージェントは、ネガティブな思考パターンを
  内在化する可能性がある
- 攻撃的な文体を蓄積する人の AI エージェントは、攻撃的な提案を出す可能性がある
- これは LLM 一般の "garbage in, garbage out" 原則の **個人レベル版**

### 4.2 「自分を映し出す鏡」としての副作用

- 自分の文体・思考傾向を AI に映すことで、**自分自身の癖を客観視できる** 可能性
  (フィードバック効果)
- 一方、AI が自分の癖を強化して返してくると、**エコーチャンバー化** する危険
- 設計上、「鏡」と「増幅器」のどちらに振るかをユーザーが選べる必要がある

### 4.3 データ漏洩時のリスクの非対称性

- 通常の IME ログ漏洩 → 「何を打ったか」が漏れる
- 個人 AI エージェント基盤の漏洩 → 「**この人が何を考えていそうか**」を再現できるデータが漏れる
- 後者ははるかに重大。**完全ローカル原則 (Section 8.6) は妥協できない**

### 4.4 心理的影響

- 「自分の入力が AI を作る」という意識が、入力行為そのものを変質させる可能性
  (パフォーマンス化、自己検閲)
- 設計上、**「AI に渡す」と「ただログを取る」を分離** し、ユーザーが意識せずに
  済む構造を作る必要がある

### 4.5 設計上の帰結

これらのリスクから、以下が必須となる:

1. **デフォルトで AI 統合はオフ** (Section 8.5 の BYOK 設計と整合)
2. **ログとエージェント供給の分離** (Section 8.6: ローカル保持 ≠ 外部送信)
3. **「学習されている内容」の可視化と削除** (Section 8.4)
4. **明示的なオプトイン UI** (どの情報を、どの AI に、いつ渡すか)
5. **データエクスポートと完全削除の保証**

## 5. 受益者の輪郭

価値とリスクを踏まえた上で、**この設計が特に効く層** を整理する。

### 5.1 強く効く層

| 層 | 効き方 |
|---|---|
| **ライター / ブロガー** | 自分の文体を AI が継承。下書き支援、リライト、要約が「自分っぽい」 |
| **クリエイター / 表現者** | 創作の語彙・トーンが AI に蓄積。アイデア出し、表現の引き出しが個別最適化 |
| **知的労働者 (ナレッジワーカー)** | 専門用語・文脈・社内語彙を AI が理解。文書作成、要約、検索が高速化 |
| **研究者 / 学生** | 自分の研究領域の語彙・引用パターンを AI が学習 |
| **コードを書く人** | コミットメッセージ、ドキュメント、Slack/Issue の文体が一貫 |

### 5.2 中立的な層

- カジュアルユーザー (SNS や私信が中心): メリットは限定的だが害も少ない
  → デフォルト OFF で本人が選択

### 5.3 注意が必要な層

- 心理的に不安定な状態の人: ネガティブな入力が増幅されるリスク
  → 警告と OFF 推奨、もしくは「鏡として見せる」モードの提供
- 業務上機密性の高い人 (法務 / 医療 / 金融): 外部 AI への送信は基本不可
  → ローカル LLM のみ可、外部 API は完全 OFF

### 5.4 表現者特化の補強

ライター・ブロガー・クリエイターは:
- 日常入力の **絶対量が多い**
- 文体に **個性が出る**
- 表現の引き出しが **AI に蓄積されると直接アウトプットに反映される**

これは「ぬこIME を毎日使う動機」と「AI エージェントが寄り添う効果」が
最も強く結びつく領域である。**初期ターゲットとして合理的** と考えられる。

## 6. 日本の AI 戦略上の意味合い (仮説)

> このセクションは **仮説** である。検証されていない戦略的主張を含む。
> 政策提言や対外発信に使う際は、各主張の根拠を別途検証する必要がある。

### 6.1 仮説: IME 経由の個別 AI 最適化は日本固有のアドバンテージになり得る

英語圏は IME を持たない。中国語・韓国語圏は IME を持つが、
**OSS ローカル IME + BYOK AI 統合** という組み合わせを真剣に追求している
プロジェクトは少ない (調査要)。

ぬこIME (および類似の OSS 日本語 IME) が、入力ログ → 個人 AI 基盤の経路を
標準化できれば、日本語ユーザーは:

- 海外の AI ツールを使う際、**自分の情報を意識的に説明する負荷が小さい**
- 同じ AI モデル (Claude / GPT 等) を使っても、**より自分に寄った応答を得られる**
- 結果として、AI の利活用速度・密度が高くなる **可能性** がある

### 6.2 仮説: AI リテラシーの底上げに寄与し得る

「AI を使いこなす」には、自分の文脈・前提・好みを AI に伝える能力が必要。
これは現状、英語圏でも上級ユーザーしか持っていない。

IME 経由で **無意識的にこれが行われる** 設計が広まれば、
意識的なプロンプト工学を経ずに AI の恩恵を受けられる層が広がる可能性がある。

### 6.3 仮説の限界

この仮説には以下の弱点がある:

- **インフラ依存**: 多くの日本語ユーザーは現在 Google IME / ATOK / macOS IME を使っており、
  ぬこIME 系の OSS 採用率が上がらなければ仮説は成立しない
- **AI バックエンド依存**: BYOK AI が普及しない / コストが下がらない場合、
  恩恵を受けるのは一部のテック層に限定される
- **文化的受容**: 「IME が自分の入力を保持する」ことへの心理的抵抗は、
  プライバシー設計の透明性に依存する
- **他言語圏との比較**: 中国語・韓国語にも同じ構造があり、日本固有では
  ない可能性 (詳細調査要)

これらの留保つきで、「**日本を AI の最先端の国にする可能性 (potential)**」
という言い方は妥当な範囲だと考えられる。「する」ではなく「し得る」。

## 8. 倫理と設計上の責任

このドキュメントが描く可能性は、ユーザーの **無意識的な入力** を資源として
扱う。これは技術的に成立しても、倫理的には繊細な領域である。

### 8.1 設計者として守るべき原則

1. **データはユーザーのもの** — ぬこIME は預かるだけ。所有権はユーザー
2. **エクスポート保証** — いつでも全データを取り出せる
3. **削除保証** — いつでも全データを消せる、第三者バックアップを作らない
4. **可視化義務** — 保持している全データを、ユーザーがいつでも閲覧できる
5. **デフォルト最小化** — ログも AI 統合も、デフォルトはオフ
6. **オプトインの明示性** — 「あとで気づいた」が無いような UI
7. **AI バックエンドへの送信前確認** — 何が送られるかをユーザーが見られる

### 8.2 やらないことの明文化

- 集約データの第三者提供 (匿名化済みでも)
- ぬこIME 公式サーバーへのアップロード機能
- 「無料で AI 使い放題」モデル (= 公式が API キーを代行する仕組み。
  Section 8.7 の OSS 持続性原則違反)
- ユーザーに無断でのデフォルト挙動変更

### 8.3 やるべきことの明文化

- データ可視化 UI (どこに何が保存されているか)
- データ管理 CLI (`nuko-data export`, `nuko-data delete --all` 等)
- 送信プレビュー機能 (外部 API に何が送られるかを送る前に表示)
- 設定の差分通知 (アップデートで挙動が変わる場合、起動時に明示)

## 9. 開発上の優先度

このドキュメントが描く未来像は、現状の開発ロードマップでは **長期** に位置する。

- 短期 (3〜6 ヶ月): IME 本体の基盤、Section 8.1 Stage 1〜2 (proptest, ログ機構)
- 中期 (6〜18 ヶ月): Section 8.1 Stage 3 (ローカル学習) と Section 8.8 L1〜L2
- 長期 (18 ヶ月〜): Section 8.1 Stage 4 (AI 統合) + 本ドキュメントの個人 AI 基盤

ただし、**思想として今書き残す価値は高い**。なぜなら:

- 設計判断の方向性が変わる (例: ログ形式を「IME 内学習用」だけでなく
  「将来 AI に渡せる形」にしておく)
- コントリビュータが集まる際の方向性として明示できる
- 「なぜ完全ローカル原則を妥協しないのか」の根拠を提供する
